## 1. 做了什么

按「208 不是默认目标、先按 150 MHz 设计降级链」的思路，把 T210 的 SDR104 从
骨架补成可上机的实现，落在驱动 `drivers/Tegra210Sdhc`：

- 时钟：PLLC4 998.4 MHz 整数分频降级链 **208(199.68) → 200(199.68) → 150(142.63) MHz**，
  任一级软件调谐出可用窗口就停；全败回 3.3 V 高速。
- Pad：SDR104 专用 pad 偏移（PU/PD=0，对应 2024 Linux 修复）在校准前显式写入，
  修复「1.8 V 默认偏移导致校准挂死」。
- 调谐：**软件 128 tap 全扫**（CMD19 + 位图 + 最大连续窗口中心），替代黑盒 auto-tune，
  位图全部落地到注册表诊断键。
- 安全：默认构建不碰 1.8 V / CAR / tuning；激活需 `NV_T210_UHS=1` + `NV_T210_UHS_ACTIVE=1`。
- 无线程/中断路径新增，全部在 SDPORT 的 quiesced 回调里执行。

## 4. 上机第一步该读什么

装激活包 → 重启 → 读
`HKLM\SYSTEM\CurrentControlSet\Services\nvtsdhc\Parameters\Diag`：

| 键 | 判定 |
|---|---|
| `Uhs1V8` | 1 = 电压切换成功 |
| `UhsPadCal` | 0 = pad 校准完成；`0xC00000B5` = 校准超时（先查这项，说明 pad 偏移需要再调） |
| `UhsTuneAttempt` | 1/2/3 = 在第几级成功 |
| `UhsTunedKhz` | `199680` 或 `142629`；`0` = 三级全败已回 3.3 V |
| `UhsTuneWindow` | ≥ 4 可用；越小越边缘 |
| `UhsTap` / `UhsTuneMap0..3` | 选中 tap 与完整 pass/fail 位图 |
| `ClockKhzActual` | 实际卡时钟 |

## 6. 待验证：蓝牙 1.8 V

朋友提醒的「蓝牙 1.8V 影响 SDR104」有物理基础了：Wi‑Fi/蓝牙是同一颗
BCM4356A3 组合芯片，UEFI 的 R390 序列在启动早期就给它上电（UART‑D + PH4），
且历史记录里 **Wi‑Fi 硬复位会打断 SD3 供电轨**（shared rail）。因此
「启动阶段 BT/Wi‑Fi 与 SD 供电交互」是这次首启挂死的第一嫌疑。
实证计划：见第九节。

## 8. 首启挂死的原因假设（按优先级）

1. **启动阶段做 1.8 V 切换/调谐**：SDPORT 在引导读盘期间就触发
   `SdSetSignalingVoltage(1.8)` + SDR104，任何一步挂住就是黑屏/BSOD。
   T214 的做法是把 SDR104 放在「静态 tuning 回调」里，不放在读盘关键路径。
2. **Wi‑Fi/BT 共享电源轨**：R390 早期给 BCM4356A3 上电，共享 SD3 供电轨；
   1.8 V IO 切换在启动阶段与它交互（朋友与历史记录都指向此方向）。
3. **`T210Signaling` 的 DAT 判断方向**：当前实现是 DAT[3:0] 非 0 就返回
   `DEVICE_BUSY`；Linux 侧是「要求为 0 才开始切压」。方向需要按 Linux 归一。
4. pad 自动校准在 T210 上挂死（SDR104 偏移已按 Linux 修复置 0，但未在真机验证）。

## 10. 2026‑11‑22 重大发现：nvtsdhc 从未绑定 SD 控制器（全部历史测试的前提错了）

11/22 上午用 SSH 直接查证了当前启动（10:28 / 10:51，winx-gpu0 BL33 11/20 固件）：

- 系统盘（ED4QT 119.2 GB SD 卡）的父链：磁盘 → `SD\...ED4QT`（sdstor）→
  **`ACPI\NVDA0212`（Service = `sdbus`，InfPath = `sdbus.inf`，驱动 10.0.22621.1）** → ACPI → HAL。
  **盘由收件箱 sdbus.sys 直接驱动**（Win11 的 SDHCI 主机驱动）。
- `nvtsdhc` 的 INF 绑定 `ACPI\NVDA0101` —— 当前 ACPI 里**没有这个设备**；
  设备管理器里只有 `NVDA0212` 和空壳 `NVDA0100`。
- `C:\Windows\INF\oem*.inf` 中**没有任何 nvtsdhc 的安装记录** → 它从未通过 PnP 安装，
  只是手工注册的服务（注册表 `Services\nvtsdhc`，Start=0，装载 `nvtsdhc.sys`）。
- 所以它是「乘客驱动」：每次开机 SCM 会加载它（DriverEntry 执行），但没有设备可绑，
  **从不参与任何磁盘 I/O**。`sc query` 显示 RUNNING 只是服务状态，不代表绑定。

### 由此解释的历史现象

1. **0xD0000FF0 全部来自驱动自己的自检**：`NV_DIAG_STOP` 在 DriverEntry 里就
   `KeSetTimer` 2.5 s，2.5 s 后若 `BlocksRead < 8` 主动 `KeBugCheckEx`。
   乘客驱动永远读 0 块 → 任何默认构建（STOP=1）一开机就自杀 → 被 Windows 降级
   （StartOverride=3）→ 下次启动用收件箱驱动 → 「能进桌面但测试全乱」。
2. minimal（13752 B，`NV_DIAG_STOP=0`）能开机与「绑定无关」，只是不自检。
3. 「UHS 首次启动挂死」的结论不成立——UHS worker 在没有 extension（未绑定）时
   根本不会排队执行，历史崩溃全是诊断/自检代码。
4. 所有 SDR104 worker 实验实际上**从未触碰过这张卡**。

### 真正的路线：先让驱动接管控制器（推荐）

1. 改 INF 匹配 `ACPI\NVDA0212`（与 NVDA0101 并列，Class 仍为 SDHost）。
2. 先用**最保守构建**接管：3.3 V HS、PIO 路径、diag 全关、STOP 关、UHS 关
   （因 `_CCA=0` 非相干控制器，ADMA 有风险，README 已有 PIO 模式）。
3. UMS 离线安装（pnputil/DISM 到 F: 离线镜像，或按历史做法写离线 SYSTEM hive），
   重启验证「机器能从我们驱动的盘启动 + SSH 可用」。
4. 绑定成功后再装延迟 worker 构建（先 300 s 写 marker 证明 worker 真的在跑，
   因为它终于有真实 slot 了），然后 pad 校准 → 1.8 V → 时钟 → 调谐。
5. 注意：延迟 worker 直接切 UHS 时，卡侧还需要 CMD6(SWITCH_FUNC)/CMD11 电压切换
   与 CMD19 调谐的发令——现有 `T210Signaling` 只做了平台寄存器部分，
   需核对并补齐协议层（或在非延迟 profile 里交给 SDPORT 发 CMD11）。

回滚安全网：`backup-20261121-sd` + ESP 下 `SwitchWOA-recover` 的 SAFE 驱动；
接管失败（0x7B）时取卡 UMS 恢复 `Services\nvtsdhc` 离线 hive 与 sdbus 绑定。

## 12. 2026‑11‑22 下午：SDPORT 路径实测（失败 → 已恢复）

### 12.1 尝试（方案 A 第一次）

- 发现并修复了能力声明顺序 bug：`NV_T210_SAFE_BRINGUP` 的置零块在 T210 UHS
  声明**之后**执行，把 SDR104/1.8V 能力抹掉 → SDPORT 一直停留在 HS
  （首测 `BusSpeed=2`、无 UHS 尝试）。修复：在置零块与 T214 块之后重新声明
  （`uhs-tree/.../nvtsdhc.c` 内 `#if NV_T210_UHS` 块）。
- 构建 `Tegra210Sdhc-uhs48`（23976 B，sha 40D92B8E…）：
  `NV_T210_UHS=1 NV_T210_UHS_ACTIVE=1 NV_T210_PIO_ONLY=1 NV_DIAG_CLOCK=1
   NV_DIAG_STOP=0 NV_T210_UHS_NO_CAR=1`（NO_CAR：不动 CAR/PLLC4，保护 GPU 时钟域；
  `t210_uhs.h` 加了 `-Wunused-function` 抑制）。
- 结果：**启动时 INACCESSIBLE_BOOT_DEVICE (0x7B)**。SDPORT 走到
  CMD6/CMD11 → 我们的 `T210Signaling` 执行 LDO2 1.8V/Pad/HC2 切换，
  但后续无法读卡；失败路径里 `T210Power3V3()` **给启动卡断电重启**，
  启动盘瞬间不可读 → 0x7B。
- 关键教训：**启动盘上做 1.8V 切换，任何一步失败都会把卡断电 → 必挂**；
  T214 能过是因为它一次通过（T214 上的 LDO2 时序/电压经过验证）。
  所以下一步必须「移出启动路径」，见第 13 节。

## 13. 下一步设计（方案 B：延迟 worker，启动路径零风险）

目标：在 nvtsdhc 已接管控制器的前提下，**开机 300 s 后**由 PASSIVE worker
在总线空闲时手动执行 UHS 序列；启动路径永远停留在 3.3 V HS。失败只会影响
运行期（重启即恢复），不会 0x7B。

需要实现（按 stage 递进，每级一个构建，都带 marker）：

1. stage0：worker 只写 marker + 读寄存器快照（证明 worker 在真实 slot 运行）。
2. stage1：主机级 CMD6（SWITCH_FUNC，access=1 group=1 value=SDR104，64B data in）
   选择 UHS 模式；卡仍在 3.3 V，验证后续 I/O 正常。
3. stage2：CMD11 电压切换握手 + 平台切换（LDO2 1.8V/PMC pad/HC2 1.8V/POWER）。
   失败时用「软回退」(LDO2 3.3V + HC2 clear + clock) 恢复，**不**用
   `T210Power3V3`（卡断电会炸运行中的系统）。
4. stage3：CAR PLLC4 199.68 MHz + SDHCI /2 → ~99.84 MHz；观察是否影响 GPU
   （PLLC4 若被 GPU 使用需要换源方案）。
5. stage4：CMD19 调谐（128 tap 或 SDHCI tuning）。
6. 全程用直接注册表写 + `ZwFlushKey`（worker 在 PASSIVE，安全；但注意
   在 SD 回调里**禁止**写注册表——旧 0x7B 的教训）。

若 stage2 多次失败：回退方案改为「启动时 SDPORT 驱动 UHS」，但用**安全的失败
路径**（失败时不碰卡电源；1.8V 失败后直接走 HC2 3.3V 恢复+回到 HS）。

### 12.4 重新接管的最快方式（已验证模板）

### 16.1 机制修复

- **空闲窗口太短**：旧实现 600 ms（240×2.5 ms），实测 35 ms 就放弃（`UhsBusy=14`）。

  （`NvT210WaitIdle`）。
- **重试**：worker 对空闲窗口最多重试 8 次（约 8 min），记录 `UhsBusyTry`。
  实测有启动连续 2 分多钟总线都在忙，第 4 轮才拿到窗口（`UhsBusy=1095`）。
- **重复延迟**：timer 已等 300 s，线程里又等一次（共 ~600 s）。已删除线程内等待。
- **线程化**：timer/DPC → 工作项只负责 `PsCreateSystemThread`；探针在专属系统线程
  里跑（PASSIVE、可长时间等待），不再占用共享工作线程。

### 16.2 实现（工作区 `D:\paopao\.tmp\uhs-tree`，构建脚本 `build-stage.ps1`）

- `T210Cmd6(s, Argument, out)`：在活控制器上发一次 CMD6。保存/恢复

### 16.4 两个试错（避免重复）

1. **CMD58(READ_OCR)/CMD8(SEND_IF_COND) 在 tran 态必然超时**
   （`0xC0000185` / `ErrorStatus=0x1` CMD_TIMEOUT），同一时刻 CMD6 却成功。
   → 这两条只在**卡识别阶段**有效，tran 态不响应，不能用来判 UHS‑I。
2. **不要在活盘总线上做 mode=1 换速**：卡一旦进入 SDR104 而主机仍停在
   48 MHz/3.3 V，系统盘 I/O 立刻出问题 → WHEA。换速必须“卡侧 + 主机侧同步完成”，
   或放到启动阶段（SDPORT 路径）一次性做掉。

### 16.5 PMIC / I2C（实锤）

- **I2C5 = `0x7000D000`**；`0x7000C500` 在 Tegra210 上是 I2C3（旧实现读回全 F）。
- **LDO2 = SD 卡 IO 轨**：`LDO2_CFG=0xF2`（sel=0x32 → 3300 mV，bit7:6 使能），
  与 UEFI `SdMmcDxe::SdPowerOn()` 的 `SetRegulatorVoltage(LDO2,3.3V)+Enable` 一致。
- 只读快照：`SD0=0x2A SD1=0x2A SD2=0x3C SD3=0x60 SD4=0x20`、
  `LDO0=0xD0 LDO1=0xC8 LDO3=0x2E LDO4=0x10 LDO5=0x2E LDO6=0xEA LDO7/8=0x05`。

**A. 修好 I2C5 后用 SDPORT 路径重试（首选）**：此前 uhs48 首启 0x7B 很可能就是

## 17. 2026‑11‑22 深夜：SDR104 首次真正跑起来（系统盘）

### 17.1 里程碑

- 系统盘现在由 nvtsdhc 驱动跑在 **SDR104 模式下**：`BusSpeed=7`（sdport.h 枚举：
  Undefined0/Normal1/High2/SDR12‑3/SDR25‑4/SDR50‑5/DDR50‑6/**SDR104‑7**），
  `UhsSpeedSeen=7`，`ClockKhzRequested=208000`（SDPORT 按 SDR104 要 208 MHz）。
- 之前所有 0x7B 的根因链（按修复顺序）：
  1. `SdhcExecuteTuning` 对 T210 是**空实现**：只置 `HC2.EXECUTE_TUNING` 就返回成功，
     位一直不清 → 控制器在后续所有传输里都处于“正在调谐”，SDR104 数据读取必崩；
  2. 能力里 `SoftwareTuning=0`（被 `NV_T210_SAFE_BRINGUP` 清零）→ SDPORT 根本不调谐；
  3. 早期（3.3 V、非 SDR104）的调谐探测会命中那个空实现并把位留死。
  修复：早期调谐请求直接成功且**不碰 HC2**；真 SDR104 时走 `T210Tune`；补齐
  `SoftwareTuning=1`。修完即可正常进桌面。

### 17.2 平台侧另外三个真 bug（都在这次定位出来）

| 位置 | 错误 | 后果 |
|---|---|---|
| I2C | `T210_I2C5_PHYS=0x7000C500`（=I2C3） | PMIC 读回全 F，1.8 V 永远切不了 |
| PMC | `0x7000E000`（=RTC） | 1.8 V IO 域序列写进了 RTC 寄存器 |
| Pad | 1.8 V 时只 OR bit12，从不清拉阻位 [3:2] | 1.8 V 下仍挂着 3.3 V 的上/下拉 |

对照物：`NintendoSwitchPkg\Drivers\SdMmcDxe\SdMmc.c`（这台机器上验证过的 3.3 V 序列，
`SD_PMC_BASE=0x7000E400`）与 `Include\Device\Max77620.h`（寄存器表）。

### 17.3 当前真实状态（活体诊断，`Live*` 键）

| 键 | 值 | 含义 |
|---|---|---|
| `UhsSigOn` / `UhsSigOff` | 1 / 1 | 我们**成功切到过 1.8 V**（status=0），随后 SDPORT 又要求切回 3.3 V |
| `LiveHc2` | 3 | SDR104 模式，但 bit3（1.8 V signalling）= 0 |

### 17.5 下一步（按收益排序）

1. **数据通路改 ADMA**：PIO 每 4 字节约 0.8 µs，天花板 ~5 MB/s；不换 DMA，时钟再高也没用。
   现有代码有 32 位 ADMA + bounce buffer 路径（0.3.0 为实现过），但当年因 `_CCA=0`
   非相干控制器风险被强制 PIO。要做就需要：bounce buffer + 严格的 flush/invalidate，

3. **CAR 升频**：`UhsCar150` 仍是 0x0F（PLLP/8.5=48 MHz）。要 SDR104 真正提速需要

4. 调谐（`T210Tune`）只有在真正 1.8 V SDR104 时才会跑（当前 `UhsTuned=0`）；

## 18. 2026‑11‑23 凌晨：SDR104“能跑但慢”，以及两个失败实验

### 18.1 已达成

- 系统盘在 **SDR104 模式**下正常进桌面并稳定运行（`BusSpeed=7`、`UhsSpeedSeen=7`、
  `ClockKhzRequested=208000`），但物理层仍是 **3.3 V / 48 MHz / PIO**：
  `LiveHc2=3`（SDR104，bit3 的 1.8 V=0）、`LivePwr=0x0F`（3.3 V）、`LiveClk=7`（/1）。
- 实测带宽（绕过缓存，256 MiB 顺序）：**读 4.2 MiB/s，写 2.4 MiB/s**。
  启动时的 3 s / 10 s 卡顿 = 12/40 MB ÷ 4 MB/s，是带宽不足，不是错误
  （`CommandErrors=1`、`ErrorInterrupts=1`）。

### 18.2 事件 trace（`UhsTrace0..3`，一字节一码）

码：`1`=SetSignaling(1.8 V) `2`=SetSignaling(3.3 V) `3`=SetSpeed(SDR104)
`4`=SdhcResetHost `5`=SDR104 下调谐 `6`=SetClock。实测序列 `4,6,4,1,3,2,4,6,3,6`。

配合开机前 32 条命令环（`UhsCmd00..07`）：

```
0,8,5,55 | 41,55,41,55 | 41,11,2,3 | 10,9,7,6 | 55,51,6,7 | 9,7,0,8 | 55,41,55,41 | 55,41,2,3
                        ↑CMD11      ↑重新识别    ↑CMD6     ↑ACMD51(SCR)  ↑CMD0 复位重初始化
```

**结论：SDPORT 走的是「CMD11 → 我们切 1.8 V → 重新识别卡 → CMD6 选 SDR104 →
做一次校验传输（ACMD51 读 SCR）→ 失败 → 退回 3.3 V → CMD0 复位重初始化 →
再以 SDR104 模式（但 3.3 V）继续」。**

失败点几乎可以确定是**未调谐的 SDR104 采样点**：trace 中没有任何 `5`，
说明 SDPORT 的调谐请求发生在电压退回之后（此时我们的分支按设计直接返回成功、
不碰 HC2），因此 1.8 V 下的 SDR104 从未被调谐过，校验传输自然出错。

### 18.3 两个失败实验（都回滚了）

1. **`NV_T210_UHS_TUNE_AT_SPEED`**：在 `SdhcSetSpeed(SDR104)` 里、电压仍为 1.8 V 时
   主动跑 `T210Tune()`。结果 **0x7B**。说明在 SDPORT 初始化中途自己发 CMD19 并折腾
   HC2 的 EXECUTE_TUNING/sampling 位，会把控制器的状态搞乱（SDPORT 期望独占该流程）。
2. **DMA（bounce buffer ADMA32）**：启动明显变流畅（DMA 本身是对的），但最终 0x7B。
   第一版把“DMA 一出错就永久 fault”照搬了 T214，而 `SdhcBuildPioTransfer` 里 fault 会让
   之后**每一笔**请求直接失败 → 整盘死。已改成「出错就退回 PIO」并新增只加速读
   （`NV_T210_UHS_DMA_WRITES=0`）+ 把 `MaximumBlockCount` 限制在 bounce 容量内，
   产物 `Tegra210Sdhc-dma3`（`659131BC`）**尚未上机验证**。

### 18.4 下一步（证据已足够，按顺序）

1. **先让 1.8 V 留住**：既然 SDPORT 的调谐请求来得太晚，就让第一次校验传输能在
   “未调谐但可用”的时序下通过。可选手段：
   - 在同一时刻把 HC2 的 `SELECT_SAMPLING_CLOCK` 置位（SDR104 采样时钟选择），
     不动 EXECUTE_TUNING、不发 CMD19——比自跑 `T210Tune` 温和；
   - 或用 48 MHz 下的“默认采样点”验证：把 `UhsSpeedSeen` 降到 SDR50/SDR25
     （只广告 1.8 V + HS），确认 1.8 V 本身能留住，再逐级加 SDR104。
2. **再测 dma3**（只加速读、出错退回 PIO）：预期读从 4.2 → 15~20 MB/s。
   上机顺序建议：先让它跑一次 `bench-raw2.ps1` 校验数据正确性，再看带宽。
3. **最后才是 CAR 升频**（PLLC4 199.68 MHz + 广告 `BaseClockFrequencyKhz=199680`，
   照 T214 `T214ParentClock` 的做法）。PIO 下升频没有收益，必须等 DMA 稳。

## 19. 2026‑11‑23 凌晨续：1.8 V 为什么留不住（已排除多项）

### 19.1 事件时间线（重要工具）

驱动里加了两条**开机能留、可离线读**的轨迹：

- `UhsTrace0..7`：**事件与命令交错**的时间线，每字节一个码。
  `1`=SetSignaling(1.8 V) `2`=SetSignaling(3.3 V) `3`=SetSpeed(SDR104) `4`=SdhcResetHost
  `5`=SDR104 下进入调谐 `6`=SetClock `7`=SDR25/SDR12 `8`=SDR50 `9`=DDR50
  `10`=CMD11 `11`=CMD0 `12`=CMD6 `13`=CMD13 `14`=CMD19 `15`=CMD7
- `UhsCmd00..07`：开机前 32 条命令（冻结，不被运行期 I/O 冲掉）。
- `UhsScr0/1`、`UhsFn0..3`：**偷看** SDPORT 自己读到的 SCR(ACMD51) 与 CMD6 功能表。
- `UhsR1_0..7`：CMD11 之后窗口内每 8 条命令的 R1。
- `UhsCmd6R1/7R1/13R1`：关键命令的 R1 原文。

### 19.2 实测时间线（三次不同构建，结果一致）

```
4 6 11(CMD0) 4 10(CMD11) 1(切1.8V) 15(CMD7) 12(CMD6) 12(CMD6) 15(CMD7) 15(CMD7) 2(切回3.3V) 4 6 11(CMD0) 6
```

即：**CMD11 → 我们切 1.8 V → 重新识别（CMD2/3/10/9/7）→ CMD6 两次 → CMD7 两次 →
SDPORT 主动退回 3.3 V → 复位 → 以 HS(3.3 V) 继续**，而且**不再重试 1.8 V**。

### 19.3 已排除的可能

| 假设 | 实验 | 结果 |
|---|---|---|
| 蓝牙/Wi-Fi 共享电源域干扰 | 禁用 `switchbt` 后重启 | **排除**：时间线完全一样 |
| pad 拉阻去掉导致 DAT 浮空、SDPORT 判定失败 | `NV_T210_UHS_KEEP_PULLS=1` 保留上拉 | **排除**：时间线一样 |
| 卡不支持 UHS-I | 偷看 SDPORT 读到的 SCR / CMD6 | **排除**：`SD_SPEC=2.00`、**`SD_SPEC3(UHS)=1`**、CMD6 `byte13=0x1F`（SDR12/SDR25/SDR50/SDR104/DDR50 全支持） |
| 卡在 1.8 V 下拒绝命令 | 窗口内 R1 | **排除**：`CMD6 R1=0x920`（TRAN、READY、无 SWITCH_ERROR/ILLEGAL/ERROR）、`CMD7 R1=0x700` 正常 |
| 只是调谐没做（SDR104 特有） | 不广告 SDR104、只广告 1.8 V 的构建 | **排除**：照样退压（SDR25 不需要调谐） |

顺带修正一个早期结论：我们自己的 CMD6 读数（`group1=0x03`）是**我们读取方式的问题**，
SDPORT 读到的同一张卡是 `0x1F`（全 UHS 模式）。

### 19.4 当前仍未定位的点

SDPORT 在“卡已正常重新识别、命令也全成功”之后主动退回 3.3 V，且不重试。
下一步需要抓**退回前最后几条命令**（当前 R1 环只存了前 8 条）：

1. 把 `UhsR1_*` 改成**滚动环**（覆盖式，退回时冻结），并保存**完整 32 位 R1**+命令号；
2. 同时记录退回瞬间的 `PRESENT_STATE`、`HOST_CONTROL2`、`POWER_CONTROL`、`CLOCK_CONTROL`；
3. 怀疑方向：SDPORT 可能在等某个“卡侧信号”（如 DAT 线电平/CMD 线空闲），
   或者它在 1.8 V 下发了某条命令后**等到超时**才判定失败（我们的 R1 捕获只覆盖成功响应）。

### 19.5 目前的最稳配置（建议日常使用）

`Tegra210Sdhc-r1win`（`A9208EE7`）：**不广告 SDR104**（`NV_T210_UHS_NO_SDR104=1`）
→ 系统盘跑 3.3 V HS（和历史上稳定态一致），带宽仍是 PIO 上限 ~4 MB/s，
但不会出现 1.8 V 反复切换/复位。带全套诊断键，方便下次继续。

## 20. 2026‑11‑23 凌晨结论：**这张卡是改标卡，1.8 V 不可能**

### 20.1 决定性证据（只读记录，无任何修改）

- `UhsOcrFirst`（3.3 V 识别阶段，6 次 ACMD41）：`0x40FF8000` → **S18A（bit24）= 0**。
  卡从一开始就声明“不接受 1.8 V 切换”。
- 1.8 V 窗口内的 ACMD41 次数 = **0**（SDPORT 切压后没再问）。
- 但同一张卡的 SCR：`SD_SPEC=2.00`、`SD_SPEC3=1`（UHS-I 版本位），
  CMD6 功能表 `byte13=0x1F`（SDR12/SDR25/SDR50/SDR104/DDR50 全报支持）——
  **能力表与真实电气能力矛盾**，是仿卡/改标卡的典型特征。
- 逆证：把 ACMD41 响应里的 S18A 强行置 1（让 SDPORT 相信支持 1.8 V），
  SDPORT 于是按 UHS 全流程走 → **0x7B 启动失败**。真实电气撑不住 1.8 V。

### 20.2 卡身份

- 标签：Samsung EVO Plus 128 GB（用户实拍）。
- 设备实际：`Generic ED4QT SD Card`，容量报 119.2 GB。
  **控制器型号与标签不符 → 改标卡**。这类卡常见问题：真实容量可能小于标称、
  写入速度虚标、UHS 能力虚报。**存放系统盘有数据风险**，建议更换。

### 20.3 对 SDR104 工作的意义（重要）

之前所有失败链（0x7B、1.8 V 被退回、SDR104 只是个标签）现在都能归因到：
**卡不支持 1.8 V，SDPORT 每次尝试后都会安全退回 3.3 V**。
驱动侧该修的 bug（I2C5/PMC 基址、pad、SpeedMode、早期调谐残留、缺失的能力声明）
都已修完，且平台序列（LDO2→1.8 V、PMC、pad、HC2、POWER）在真机验证通过：
切压瞬间 `Hc2=0x0008`（1.8 V 位已置）、`Power=0x0B`、`PredentState=0x01FB0000`、
`IntStatus=ErrStatus=0`、窗口 31–62 ms、CMD11 后重新识别成功。

**下一步只有两条路：**

1. **换一张真 UHS-I 卡**（正品 Samsung EVO Plus / SanDisk Extreme 等），
   然后直接用 `NV_T210_UHS + SLOT_CAR` 构建（PLLC4 199.68 MHz + 广告基频）验证；
   预计 SDPORT 会自己走完 CMD11→1.8 V→SDR104→调谐（T214 已验证同一套流程）。
   届时还要把 `SdhcExecuteTuning` 的 T210 分支接上 `T210Tune`（128-tap 软件调谐）。
2. **不换卡时的提速**：走 **3.3 V HS + ADMA**（不需要 1.8 V）。
   PIO 天花板 ~4–5 MB/s，DMA 后预期 15–20 MB/s。
   之前 DMA 两次 0x7B 的构建里混着 UHS 尝试，应做**纯 HS、不广告 UHS**的 DMA 构建隔离。

### 20.4 当前稳定配置

`Tegra210Sdhc-ocr`（`B8D8ADE7`，3.3 V HS，带全套诊断）已正常进桌面；
日常使用建议回到 `Tegra210Sdhc-r1win`（`A9208EE7`）或直接沿用 `ocr` 版。

## 21. 2026‑11‑23 清晨：内联 PIO 提速（3× 写 / 1.3× 读，已验证正确）

### 21.1 为什么 PIO 只有 4 MB/s

原 PIO 内层是**每 4 字节一次外部函数调用**（`SdhcReadRegisterBufferUlong` →
`SdPortReadRegisterBufferUlong`），而数据口是 FIFO：一次只能读一个 dword。
函数调用开销把 48 MHz×4bit = 24 MB/s 的总线能力吃掉了 5/6。

注意 `NV_PIO_BUFFERED=1` **不能开**：它用 `READ_REGISTER_BUFFER_ULONG` 读的是**连续地址**
（0x20、0x24…），而 FIFO 必须重复读同一地址 —— 这大概就是 0.2.3~0.2.5 那些
`WHEA_UNCORRECTABLE_ERROR` 的来源。

### 21.2 改法与结果（`NV_T210_FAST_PIO=1`）

`SdhcReadDataPort` / `SdhcWriteDataPort` 改成内联的
`READ_REGISTER_ULONG` / `WRITE_REGISTER_ULONG` 循环（同一地址重复访问，语义不变）：

| 项目 | 之前 | 之后 | 倍数 |
|---|---|---|---|
| 顺序写（256 MiB，绕过缓存） | 2.4 MiB/s | **7.2 MiB/s** | 3.0× |
| 顺序读（256 MiB，绕过缓存） | 4.2 MiB/s | **5.5 MiB/s** | 1.3× |
| 复制 48.7 MiB 文件 | — | 5.5 MiB/s | — |
| **SHA256 比对** | — | **完全一致** | ✅ |

### 21.3 ADMA 仍被卡住的真实原因（这次查清了）

- 我加了「**先自检、通过才启用 DMA**」的机制（`T210DmaSelfTest`：同一扇区用 ADMA 读一次、
  PIO 读一次，逐字节比对；不一致就永久退回 PIO）。设计上开机全程只用 PIO，DMA 在
  开机 45 s 后才试探，**所以带 DMA 的构建现在能正常开机**（实测 `UhsDmaOk=0`，
  5 万+ 请求全部安全走 PIO）。
- 但自检拿不到机会：`dmaSt = pioSt = STATUS_DEVICE_BUSY` —— SDPORT 是系统盘的宿主，
  总线几乎没有 1 ms 空闲窗口（这张卡只有 4~5 MB/s，队列常满）。
- `UhsSmmu=0`（MC 0xA88 读回 0）暗示 SMMU 翻译是关的，物理地址本应可用；
  但**无法在不影响开机的前提下验证**，所以 DMA 目前仍不可用。

**若要继续 DMA**，两条可行路线：
1. 用 `IoGetDmaAdapter` + `AllocateCommonBuffer` 拿**设备可见地址**（SMMU/IOMMU 正确映射），
   而不是物理地址；这需要拿到 FDO，sdport 不直接提供，需要额外手段。
2. 或者接受「DMA 依赖 SDPORT 的 SG 请求」：不再强留 PIO 契约（`NV_T210_PIO_ONLY=0`
   + `ScatterGatherDma=1`），让 SDPORT 自己建 SG 表并使用它自己的 DMA 适配器 ——
   但历史上正是这条路在本控制器上（`_CCA=0`）读不了启动盘。

### 21.4 当前推荐配置

`Tegra210Sdhc-fastpio`（`78D72E55`）：不广告 UHS、不动 CAR、内联 PIO、
读写分别为 5.5 / 7.2 MiB/s，数据校验通过。日常使用就用这一版。

## 22. 2026‑11‑23 白天：eMMC（SDMMC4）实验与 DMA 自检基础设施

### 22.1 eMMC 为什么没做成（三组实验的完整证据）

UEFI 的 DSDT 里其实**早就写好了 eMMC 设备**（`Device (SDM4)`，`0x700B0600`，GSI 0x3F），
默认 `_STA=0` 隐藏，只有 `-D SWITCH_ACPI_EMMC=1` 才可见。我们把它打开并逐组测试：

| 尝试 | 结果 | 原因分析 |
|---|---|---|
| `_CID = PNP0D40`（标准 SDHCI 兼容 ID） | **WHEA_UNCORRECTABLE_ERROR** | 收件箱 `sdbus` 立刻抢绑这个 `_CCA=0` 控制器；这和 2026‑11‑13 那次 sdbus 崩溃同源 |
| `_CID = NVDAEMMC` + 完整 `_CRS`(MMIO+GSI 63) | 卡在 Windows 转圈不结束 | 资源声明（很可能是 GSI 63 与现有设备冲突）导致启动挂起 |
| `_CID = NVDAEMMC` + **无 `_CRS`** | **0xC000000F**（BCD/启动卷读取失败） | 设备没有任何资源，Windows 引导阶段读不到启动卷 |

**结论：eMMC 缺的不是 ACPI 的一个开关，而是两个组件：**

1. **Windows 侧 eMMC 驱动**。`nvtsdhc` 目前只实现 SD 协议（CMD8/ACMD41/CMD6/CMD19…）。
   eMMC 需要：`CMD1` 初始化、`EXT_CSD` 读取、`CMD6` 切换、**8-bit 总线**、
   HS200/HS400 与 `CMD21` 调谐 —— 与 SD 路径并行但独立的一套。
2. **UEFI 侧 eMMC 支持**。`SdMmcDxe` 的 eMMC 分支是 `ASSERT(FALSE)` 占位，SDMMC4 也没有初始化；
   即便系统装在 eMMC 上，引导阶段同样没有代码能读。

正确顺序应是：**先写驱动/UEFI 通路 → 验证能读写 eMMC → 最后才迁移系统**。
先把设备“亮”给 Windows 只会破坏 SD 启动路径。

### 22.2 有用的副产物

- 构建流程（Windows 原生）：devkitPro MSYS2 + edk2 `build.py`，必须
  `PYTHON_COMMAND=/usr/bin/python3`（否则 Windows python 产生反斜杠路径被 sh 吃掉），
  PATH 里 `WoA/build/toolwrap` 要在 devkitA64 之前。
- **`Dsdt.asl` 千万不要用 PowerShell `Set-Content -Encoding utf8` 保存**：会写入 UTF‑8 BOM，
  预处理后变成 `\U0000feff`，iasl 直接语法错误（`Error 6126`）。要用无 BOM 写入。
- `-n 24` 并行（16 核 32 线程）把 BL33 构建从 ~14 分钟压到 **~5 分钟**。

### 22.3 卡的带宽潜力已被证实

hekate 的 USB UMS 模式实测这张卡：**写 22 MB/s、读 37 MB/s**（任务管理器截图为证）。
SDMMC1 4-bit @48 MHz 的理论上限约 24 MB/s，说明 hekate（用 ADMA2）已经跑满。
**因此 22 MB/s 是我们驱动的合理目标**，当前 PIO 只有 5.5/7.2 MB/s，差距全在实现效率。

### 22.4 DMA 自检基础设施（已就位）

`T210DmaSelfTest` + 定时器/工作项/线程已实现：
- 开机全程 PIO，**定时器到期后**才做「同一扇区 ADMA 读 vs PIO 读」逐字节比对；
- 只有完全一致才把 `T210DmaOk` 置 1，此后 `T210BuildDma` 才真正接管；
- 结果写 `UhsDmaTest`（`1`=通过；`0xE002`=ADMA 读失败；`0xE003`=数据不一致，
  高 16 位是不匹配字节数；`0xE004`=始终没有空闲窗口；`0xE005`=PIO 读失败）。

**待解决**：定时器到期后线程没有产生任何 Diag 键（`UhsDmaBeat` 心跳也未出现），
说明定时器→DPC→工作项→线程这条链没有跑通，需要下一步定位
（已加入 `UhsDmaBeat` 心跳并把延迟缩到 120 s 便于快速二分）。

## 23. 2026-11-23/24：真正的瓶颈是时钟；PIO 挖到底；物理地址 DMA 路线终结

### 23.1 之前所有记录里的 “48 MHz” 都是假的（本次最重要的发现）

- **旧代码的模型**：`CAR = PLLP 408 ÷ 8.5 = 48 MHz`，于是把主机分频器
  `SDCLK Frequency Select` 写成 0，认为那是 `/1`，Diag 里也一直报
  `BaseClockKhz=48000`、`ClockKhzActual=48000`。
- **真实硬件是两处都错、且不能互相抵消**：
  1. CAR 的分频项是 `(字段 + 2)`：字段 15 → `408/17 = 24 MHz` 进控制器（不是 48）；
  2. SDHCI 的规则是 `SDCLK = 输入 / (2 × SELFREQ)`，`SELFREQ = 0` 表示 **÷2**（不是 ÷1）
     → 卡实际只拿到 **12 MHz**。
- **铁证（实测）**：读路径每 512 字节块的搬运耗时 **85.5 µs**，而 4-bit @12 MHz 的
  理论值是 **85.3 µs** —— 严丝合缝。
- **旁证**：同机 UEFI 参考实现 `NintendoSwitchPkg/Drivers/SdMmcDxe/SdMmc.c`
  `tegra_mmc_change_clock()` 写的就是 `div = ceil(rate/clock); div >>= 1;`，
  同一个 ÷2 规则。
- 顺带纠正历史记录：hekate UMS 的 22 MB/s 是在**真实 48 MHz + ADMA2** 下跑出来的，
  不是我们这个虚报的 “48 MHz”。

### 23.2 修复与实测

- `NV_T210_CAR_DIVISOR`（新增编译期开关，默认沿用旧值）：
  设 0 → `CAR = 408/2 = 204 MHz`；同时 `BaseClockFrequencyKhz` 报**真实**的 204000。
- `SdhcCalcClockFrequency` 的 spec-3 分支重写为
  `D = round(base / (2 × req))`、`D ≥ 1`（永不写 0）、`Actual = base/(2D)`。
- 实测：SDPORT 请求 50 MHz → `D=2` → **`ClockKhzActual = 51000`**，
  `RegClockControl = 0x0207`（SELFREQ=2），`CarSdmmc1Before=0x1F(12.4M)`
  → `CarSdmmc1After=0x00(204M)`；全程 `CommandErrors` 只有开机那条 CMD5，
  **没有新增错误** —— 说明这张“改标卡”在 51 MHz / 3.3 V 下是稳的。
- **但读带宽没变**（见 23.4）——时钟不再是瓶颈。

### 23.3 写路径的编译条件 bug（真实收益，1.8×）

`SdhcWriteDataPort` 里的 FAST_PIO 内联 FIFO 写循环被错误地嵌在
`#if NV_PIO_BUFFERED`（=0）里面，所以**写一直在走“每 4 字节一次 SDPORT 外部调用”
的慢路径**，而读路径在条件之外、是快的。把它移到 `NV_PIO_BUFFERED` 之外后：

| 版本 | 顺序写 | 顺序读 |
|---|---|---|
| 慢写循环（12 MHz） | 2.49 MiB/s | — |
| 快写循环（12 MHz） | **4.45 MiB/s** | 5.14 MiB/s |
| 快写 + 51 MHz | **4.86 / 5.47 MiB/s** | 5.08 MiB/s |
| 快写 + 51 MHz + 128 块/次 | ~5.2 MiB/s | **5.83 MiB/s** |

### 23.4 PIO 分段计时（新增 Diag 键，定位到每块开销）

新增只读计数器：`PioCalls / PioCallBlocks / PioMore / PioReadyMiss /
PioBudgetHit / PioPollIters / PioPollUs / PioPortUs / PioCallUs`
（在 `SdhcStartPioTransfer` 里按块累加，不受上层请求对象复用影响）。

| 状态 | 数据口搬运 | buffer-ready 轮询 | 每块总时长 | 说明 |
|---|---|---|---|---|
| 12 MHz | **85.5 µs/块** | — | ≈94 µs | 完全由总线决定 |
| 51 MHz | **57.2 µs/块** | 0.85 µs/块 | ≈94 µs | 变成 **MMIO 每 dword ≈447 ns** + **每块 1 次中断** |

结论：**PIO 的天花板约 9 MB/s**（57 µs/块），抬时钟对它没用。
另外 `Interrupts / PioCallBlocks ≈ 1.0`，说明即使一次调用搬 30~44 块，
控制器仍然每块发一次 buffer-ready 中断 —— 这部分开销在 miniport 之外。

### 23.5 每轮搬运块数：32 → 128

`NV_PIO_POLL_BLOCKS` 32 时，SDPORT 每个约 55 块的数据命令至少要一次中断往返：

| 指标 | 32 块/次 | 128 块/次 |
|---|---|---|
| 平均块/调用 | 29.5 | 43.9 |
| `PioMore`（未搬完就返回） | 87% | 21% |
| 顺序读 | 5.15 MiB/s | **5.83 MiB/s** |

### 23.6 物理地址 DMA（ADMA32 + bounce buffer）路线：**结论是致命不可用**

探针设计（`T210DmaProbe`）：在**数据命令完成后的请求 DPC 里**（那一刻总线由我们持有、
无需等空闲窗口）发一条 `CMD17` 读 LBA0 进 bounce buffer（ADMA），再发一条同样的
`CMD17` 走数据口（PIO），逐字节比对，并额外校验 NTFS 引导扇区签名
（偏移 3 的 `NTFS` 或 510/511 的 `55 AA`）。只有全对才置 `T210DmaOk=1`。

门限历经三次修正：
1. 定时器 +120 s（`dmaprobe3`）→ 启动约 2 分钟后挂；
2. 时间 +300 s + ≥20000 数据命令 + 总线空闲 3 s（`dmaprobe5`）→ 桌面挂；
3. 时间 +300 s + ≥20000 数据命令 + **≥8 块读**触发（`dmaprobe7`）→ 桌面挂
   （发现 NTFS 预读会把 4608 字节的读改写成 32/64 块命令，所以“恰好 9 块”的触发不可能成立）。

**三次结果完全一致**：探针门限一到，**盘立刻死**（桌面画面还在、但所有新 I/O 挂住、
SSH 卡在 `banner exchange`、ping 仍通）；离线 hive 里 `UhsDmaTest=0`，
**连探针入口的 `UhsDmaProbeCalls` 标记都没落盘**（`DataCommands` 停在
`0x8000/0xD800` 这类保存边界）——说明第一条裸 ADMA 读就把控制器打死，
连后面那条注册表写都来不及。

**结论：这台 `_CCA=0` 的机器上，用物理地址喂 ADMA32 是不可用的，而且是“致命”
不可用**（SMMU 一旦翻译，ADMA 会朝不可预期的物理页写字；或者控制器状态被打乱）。
不再尝试这条路。

若以后还要 DMA，唯一正确的方向是 **SDPORT 的 SG-DMA**
（`SdTransferMethodSgDma`：地址来自 sdport 的 DMA 适配器、是设备可见地址），
需要单独评估 `_CCA=0` 下的 cache 维护问题，且**不能**再用“注入裸命令”的方式做验证。

### 23.7 SDR104 结论（未变，本卡无解）

3.3 V 识别阶段 6 次 ACMD41 的 `S18A(bit24)` 全为 0 → 卡自己声明不接受 1.8 V 切换；
SDPORT 每次尝试后都安全退回 3.3 V。驱动侧的 1.8 V 序列（LDO2/PMC/pad/HC2/调谐/
能力声明）都在真机验证通过了，缺的是一个**正品 UHS-I 卡**。

### 23.8 当前稳定配置（日常用这一版）

`build/Tegra210Sdhc-blk128`（32680 B，sha `41EFF78A`）：
3.3 V HS、**51 MHz**、内联 PIO、128 块/次、带全套 Diag；
读 **5.83 MiB/s**、写 ~5.2 MiB/s，无新增错误。

### 23.9 两条恢复踩坑（务必记住）

1. **离线读 hive 必须用 `reg query`，不能用 `Get-ItemProperty`**：
   PowerShell 注册表提供程序会占着句柄，导致 `reg unload` 失败、hive 卸不掉，
   于是 Windows 认为卡被占用、**弹不出卡**。
   脚本已改：`restore-good-driver.ps1`（顺带先抓 Diag 证据、再换驱动、最后强制卸载 hive）。
2. **Windows 在这张 5 MB/s 的卡上做更新/用户初始化会持续很久**（10 分钟以上黑屏或
   “进系统很慢”），此时 SSH 会是 `banner exchange` 超时、但 ping 仍然通。
   这与“驱动把盘搞死”的现象**一样**，需要用离线 Diag 有没有探针标记来区分。

### 23.10 复盘：那两次“进系统很慢 / 黑屏”到底是什么（证据链）

用离线方式读卡上的事件日志（`F:\Windows\System32\winevt\Logs\*.evtx`，
需要管理员权限复制出来，再用 `Get-WinEvent -Path` 解析），把每一次启动的
「内核启动(Kernel-General 12) → 事件日志服务就绪(EventLog 6005)」算出来：

| 启动时刻 | 服务就绪用时 | 当时卡上的驱动 | 探针条件 |
|---|---|---|---|
| 18:30 / 18:40 | 1.8 / 1.9 min | dma13（旧） | — |
| **20:11** | **12.3 min** | pio2（**无探针**） | 不可能触发 |
| 20:49 / 21:00 / 21:12 | 2.0 / 1.9 / 2.1 min | clk51、dmaprobe2（触发写错） | 否 |
| **21:27** | **31.5 min** | **dmaprobe3（120 s 门限，启动中触发）** | **是** |
| 22:12 / 22:29 | 3.5 / 4.1 min | dmaprobe5/6 | 否（300 s 门限在服务之后就绪） |
| 22:48 | 0.6 min 后挂死 | dmaprobe7 | 是 |

**结论分两部分**：

1. **20:11 那次 12.3 分钟是纯 Windows 侧**：`SoftwareDistribution\ReportingEvents.log`
   显示 `TrustedInstaller FOD` 在 18:59 / 19:05 / 19:51 / 20:00 反复
   `[AGENT_DOWNLOAD_RESUMED]`（03:19 还有一次 `[AGENT_DOWNLOAD_CANCELED]` 8024000b）——
   即 Windows 在这张 5 MB/s 的系统盘上反复下载/续传一个按需功能包，
   配合 TiWorker/CBS 会把启动拖到十几分钟。当时驱动是 pio2，**探针不可能跑**。
2. **21:27 那次 31.5 分钟是 DMA 探针**（dmaprobe3 的 120 s 门限在启动过程中就打开了），
   22:48 那次 0.6 分钟就挂死也是探针。其余所有非探针启动都是 1.8–2.1 分钟。

**顺带发现的启动拖累（与驱动无关，长期存在）**：每次开机都有三个服务超时——
`SwitchWOABringup` 45 s、`Tailscale` 45 s、`Microsoft Edge Update Service` 30 s，
合计约 2 分钟。想缩短开机可以单独处理这三项。

**建议**：做驱动实验期间把 Windows Update / FOD 下载暂停（或把网络标记为计量连接），
否则 5 MB/s 的盘上任何后台下载都会污染带宽与启动时间的测量。

**判据（以后区分“盘被驱动搞死”和“Windows 自己慢”）**：
- 盘被驱动搞死：ping 通、SSH 卡在 `banner exchange`、离线 Diag 里的计数器**不再增长**；
- Windows 自己慢：同样 SSH 不通，但离线 Diag 的 `DataCommands/BlocksRead` 在增长（说明盘在干活）。

## 24. 2026-11-24：**SG-DMA 打通，读 5.8 → 30 MiB/s（5 倍）**

### 24.1 为什么这条路能成，而 23.6 那条不能

- **失败的那条**：我们自己用 `MmAllocateContiguousMemorySpecifyCache` 拿一块
  bounce buffer，把**物理地址**写进 ADMA 描述符。这台控制器 `_CCA = 0`，
  SMMU 一旦翻译，物理地址就不是设备可见地址 → 三次实验每次都把盘打死。
- **成功的这条**：让 **SDPORT 自己建散列列表**（`SdTransferMethodSgDma`）。
  描述符表地址来自 `Request->Command.DmaPhysicalAddress`，散列元素地址来自
  `Request->Command.ScatterGatherList` —— 都是**经过 sdport DMA 适配器映射的设备可见地址**，
  SMMU 翻译由上层正确完成；cache 维护也由上层负责。
- **旁证（早就存在）**：接管前这台机器一直由收件箱 `sdbus` 驱动跑 ADMA 从同一张卡启动，
  证明该控制器 + `_CCA=0` 的 DMA/缓存链路本来是通的，之前失败的是我们自己的地址来源。

### 24.2 实现：只差一个能力声明

代码本来就有完整 SG-DMA 通路（`SdhcSetTransferMode` 的 `SDHC_TM_DMA_ENABLE`、
`SdhcBuildAdmaTransfer`、`SdhcCreateAdmaDescriptorTable`、
`SdhcResetHost` 里的 `HOST_CONTROL` ADMA 选择位），缺的只是
`NV_T210_PIO_ONLY=1` 把 `Supported.ScatterGatherDma` 挡住了。改动：

1. `build-stage.ps1` 新增 `-SgDma`（→ `NV_T210_PIO_ONLY=0`）。小于 64 字节的传输
   （SDIO/CMD6 等）仍走 PIO，大块传输走 ADMA2-32bit。
2. 新增 Diag 计数器：`SgDmaRequests / SgDmaBlocks / SgDmaErrors /
   SgDmaErrStatus / SgDmaAdmaErr`（在 `SdhcBuildAdmaTransfer` 与错误 DPC 里累加）。
3. 产物：`build/Tegra210Sdhc-sgdma1`（33192 B，sha **`57E79836`**），
   配置 = 51 MHz + `NV_PIO_POLL_BLOCKS=128` + 内联 PIO（小块用）+ SG-DMA（大块用）。

### 24.3 实测（同一张卡、同一次开机）

| 项目 | PIO（blk128，51 MHz） | **SG-DMA（sgdma1）** | 倍数 |
|---|---|---|---|
| 顺序读 192 MiB ×3 趟 | 5.83 MiB/s | **29.5 / 30.9 / 33.2 MiB/s** | **5.0–5.7×** |
| 顺序读 256 MiB | — | **24.0 MiB/s** | — |
| 顺序写 128 MiB ×2 趟 | ~5.2 MiB/s | **5.72 / 13.16 MiB/s** | 1.1–2.5× |
| 顺序写 256 MiB（含 flush） | — | **10.43 MiB/s** | — |
| `SgDmaErrors` / `SgDmaAdmaErr` | — | **0 / 0** | — |
| 数据完整性 | SHA256 一致 | **SHA256 一致（64 MiB 与 256 MiB 两次）** | ✅ |

寄存器侧确认：`RegHostControl = 0x22`（4-bit + **DMA 选择 bits5:4 = 10 = ADMA2-32bit**）、
`ClockKhzActual = 51000`、`CarSdmmc1After = 0x00`。

### 24.4 遗留疑点（下次要注意）

1. **实测读速率 33 MiB/s 已经超过“51 MHz × 4bit = 24.3 MiB/s”的理论上限**。
   说明 CAR/SDHCI 的分频模型还有偏差：真实 SDCLK 很可能是 **~102 MHz**
   （即 CAR 分频字段 0 实际是 `÷1` 而非 `÷2`，`SELFREQ=2` → 408/(2×2)）。
   也就是说这张卡现在被**超频**驱动（HS 卡标称 50 MHz）。当前证据是「零错误 + 两次 SHA256 一致」，
   但**长期可靠性未验证**：若出现 CRC 错误/掉盘，第一步就是把 CAR 分频调高降速。
   记录里那个「12 MHz 与 85.3 µs 完全吻合」的旧证据与 `÷1` 模型只有 6% 偏差，两种模型都能解释老数据，
   新数据（超理论值）更支持 `÷1`。
2. 写入仍被卡本身限制（这张改标卡写入本来就慢，hekate 下也只有 22 MB/s 的写）。
3. 日常观察点：`SgDmaErrors`、`CommandErrors`、以及是否出现 I/O 卡顿；
   一旦异常先降时钟再过一遍 SHA256。

### 24.5 当前推荐基线

`build/Tegra210Sdhc-sgdma1`（33192 B，sha `57E79836`）= **51 MHz + 128 块 PIO + SG-DMA**。
读 ~30 MiB/s、写 ~10 MiB/s，数据校验通过。回退版仍是 `blk128`（`41EFF78A`，纯 PIO 5.83/5.2）。

### 24.6 2026-11-24 实测补充：任务管理器读到 **48 MB/s**，时钟模型定案

用户在桌面上开 Edge 时，任务管理器显示磁盘读 **48 MB/s**（≈45.8 MiB/s）。
4-bit 总线要跑到 48 MB/s 需要 **96 MHz** 的 SDCLK，因此：

- **CAR 分频字段 0 的真实含义是 `÷1`**（即输入就是 408 MHz），`SELFREQ=2`
  → `SDCLK = 408/(2×2) ≈ 102 MHz`；实测 96–102 MHz（含协议开销）完全吻合。
- 于是 23.1 里“字段 = `(f+2)`”的模型对新数据不成立；当年那个
  “12 MHz ↔ 85.3 µs 严丝合缝”的旧证据在 `÷1` 模型下是 12.75 MHz（偏差 6%），
  两种模型都能解释旧数据，**新数据（超过 51 MHz 理论值）只支持 `÷1`**。
- **重要更正**：Diag 里的 `ClockKhzActual = 51000` 是驱动按错的模型算出来的，
  **真实卡时钟约 102 MHz** —— 这张 HS 卡（标称 50 MHz）现在处于**两倍超频**状态。
- 参考：48 MB/s 已超过 hekate UMS 的 37 MB/s（同卡同 4-bit）。

**两个现成的构建**：

| 构建 | CAR 字段 | 真实 SDCLK | 读速率 | 定位 |
|---|---|---|---|---|
| `Tegra210Sdhc-sgdma-stable`（`57E79836`） | 0 | **~102 MHz（超频）** | 30–48 MB/s | 当前在用，性能优先 |
| `Tegra210Sdhc-sgdma51`（`B506C640`） | 1 | **~51 MHz（规范内）** | 待测（预计 ~24 MiB/s） | 保守/长期可靠备选 |

**判断规则**：若在 `sgdma-stable` 下出现 CRC 错误、`SgDmaErrors` 非 0、I/O 卡顿或掉盘，
直接换 `sgdma51`（一次部署 + 一次重启，绑定与其它配置不变）。
