# switchjoycon 交接（2026-11-17 上午，供新会话直接接手）

> 前一个会话已到长度上限，开新会话请先读这一页 + `ref/PROTOCOL.md`。

## 一、这个项目要做什么

Nintendo Switch 初代机（Erista）运行 **Windows 11 ARM64**（SWOA 项目），要做**导轨 Joy-Con 手柄驱动**：
左右手柄插在机身上时，通过 **UART-B / UART-C** 与主机通信（1 Mbaud、反相），驱动解析协议后通过 **VHF** 暴露 HID。
参考实现：switchroot `joycon-serdev.c`（已下载在 `ref/`）。

## 二、已经跑通的部分（重要：这些不要重做）

| 环节 | 状态 | 关键点 |
|---|---|---|
| 固件 ACPI | ✅ | `Dsdt.asl` 里 `UAR2`(右, 0x70006040, IRQ **69**) / `UAR3`(左, 0x70006200, IRQ **78**)，各带 `JINI(1)` AML：pinmux + 精确 16 MHz 时钟（`CLK_SOURCE = (1<<24)|49`，2×408/(49+2)）+ 充电使能 |
| 中断号 | ✅ | **Tegra210 UART-B = GIC SPI 37 → GSIV 69；UART-C = SPI 46 → GSIV 78**（曾误用 101/102） |
| 协议帧 | ✅ | 帧头 **12 字节**（`magic[3]=19 81 03 + size + pad + cmd + hdr[5] + crc`），CRC8 poly 0x8D 覆盖 pad..hdr 共 7 字节；0xA5 握手帧 CRC 写 0 |
| 握手流程 | ✅ | `A1 A2 A3 A4` → `0xA5 hdr=02 01 7E`（只比命令字节！）→ `0x91 hdr=01` 读 MAC（回 `0x94`）→ `0x91 hdr=11/10` HID 断开/连接 → `0x91 hdr=12 04 00 00 12` data `0F 00 00 00` → 子命令 `0x03` 设报告模式 0x30 → Ready |
| 输入报 | ✅ | 只解析 **`0x30`**（`0x21` 子命令应答在相同偏移是应答数据，当成按键会随机误触） |
| HID 输出 | ✅ | `joy.cpl` 里能看到两个 `虚拟 HID 框架(VHF) HID 设备`，按键/轴都有反应 |
| 自校准 | ✅ | 进 Ready 后取前 32 帧原值平均做摇杆中心；指针死区 6000（约 18%） |
| 设备绑定 | ✅ | Windows 不会自动升包：**设备管理器"更新驱动程序"选 `C:\SwitchWOA\drivers\switchjoycon`** 才能换版本；`pnputil /restart-device` 不换包 |

### 这轮踩的坑（别再犯）

| 版本 | 我加的 | 后果 |
|---|---|---|
| 0.3.0 | 指针"轴跳变过滤" | 快速推杆时指针拿到上一帧旧值 → **不同步/朝一个方向走**（0.3.14 才删掉）|
| 0.3.2 | 40 死区 + 自校准防污染 | 死区太小盖不住；自校准仍可能定错中心 → 恒偏 → 指针持久爬行 |
| 0.3.3 | SPI 工厂校准 | 本机 rail 上那 9 字节与实测不符，**不能用** |
| 0.3.4/0.3.10 | 自适应中心（持续修正） | 中心一直在动 → 轴输出跟着变，表现为"越用越偏" |
| 0.3.8/0.3.9 | 指针重写 + `if(step<1) step=1` | 那行强制最小值让"刚过死区"变成**每帧 1 格的持续爬行** |

| **0.3.16** | 中心**跨重握手粘住**（`CalValid`，只有 D0 上电才清）：右手柄一条样本里 `timeouts=105`，每次重连都把中心清回 2048 → 轴"突然偏"，等新窗口采完又"自己好" |
| **0.3.17** | ① 采纳中心前必须落在 **2048±600**（真机静止值 X 1540~2280、Y 1540~2270）；② **运行时自检**：存着的中心跑出该区间（如老版本留下的 Y=944）立即作废重测 —— 否则会长期卡在 -19894 这种读数；③ 死区 150 → **200** |
| **0.3.18** | 删掉"连续拒绝 20 次后接受并夹取"的兜底 —— 它把不该接受的量（Y 夹成 1448）强塞进中心，造成 -15899 恒偏。现在**只接受 2048±600 内的静止窗口**，量不到就继续用 2048（200 死区能吸收真机常规偏移）。实测：`centre=raw`、静止 `HID=(0,0)`、推到底 `HID=±32000`、8 秒无操作时鼠标位移报告 **+0** |

### 0.3.18 的最终参数（用户实测"玩了半天没问题"）
- 摇杆：32 帧平均定中心（**静止门槛** spread≤60 + **合理区间** 2048±600 + 跨重连粘住 + 运行时自检）
- 死区：**200 个读数**（≈20% 半量程）
- 指针：0.2.9 原算法（速度×毫秒），静止不发任何位移
- 诊断（每秒 1 次）：`JcCentre / JcRaw / JcHid / JcCalTries / JcCalValid / JcMouseSent / JcTimeouts / JcRxErr`

### 性能（用户问）

- 静止门槛本身：每个报告 4 次比较 + 每 32 个报告 2 次整除 → 63 报/秒下约 0.0001% CPU，可忽略；
- 驱动真正的大头是 **Ready 状态 2 ms 轮询**（每设备 500 次/秒唤醒）与**每秒一次的注册表诊断写入**（0.3.0 之前是 ~6000 次/秒，那才是问题）；
- 实测空闲 CPU 0.0~3.2%，内存 3.8 GB/2.1 GB 空闲。

## 三之二、0.3.0 做了什么（按证据，不是猜）

现场证据：左手柄 `JcReports=29954 / JcTimeouts=1`，**右手柄 `JcReports=835 / JcTimeouts=442`** ——
右手柄链路一直在"掉线→重握手"，说明导轨上的字节流确实有坏帧，而 0.2.9 的解析器**没有任何帧完整性校验**，
坏帧里的随机字节被当成 `button_status`，于是出现"没按 ZL/ZR 却触发"、"光标突然跳一段"。

0.3.0 的六处改动：

| # | 改动 | 原因 |
|---|---|---|
| 1 | **RX 帧 CRC 校验**：`Packet[11] == crc8(Packet[4..10])`，Ready 期不通过直接丢帧并让帧装配器重新找 `19 81 03` | 用实测帧 `19 81 03 07 00 a5 02 02 7d 00 00 64` 反推验证过（crc 正是 0x64），握手期放宽以免影响 bring-up |
| 2 | **长度校验两处**：帧头 `Packet[3]+5 == Length`；0x30 载荷必须是 `13 + 12n`（n=0..4） | 用户看到的"长度 20"这类帧根本不可能来自 `0x30`，是错帧标志 |
| 3 | **修掉双倍喂字节**：轮询直读循环原来既 `JcFeed()` 又把字节塞进环形缓冲，下一轮再喂一遍 → 每个字节被解析两次、帧与自己的副本交错 | 这是"偶发乱跳"的结构性原因之一 |
| 4 | **LSR 错误字节丢弃**：读字节时若 `LSR & 0x1E`（overrun/parity/framing）就丢该字节并让装配器重新同步 | 1 Mbaud + 反相，坏字节必须有出口，否则一个坏字节污染后面所有帧 |
| 5 | **指针防抖**：鼠标键必须连续 2 帧一致才生效；摇杆两帧间跳变 >12000 视为坏帧，沿用上一帧值 | 人按不出 1 帧（15 ms）的点击；真摇杆 15 ms 也走不了那么多 |
| 6 | **注册表不再每 2 ms 写**：诊断值统一进 1 s 窗口（原代码每轮询写 ~12 个值 = 6000 次/秒 I/O） | 这台机器 I/O 本来就紧，狂写注册表会拖慢整个导轨线程 |

另外：子命令里的 rumble 段改成中性包 `00 01 40 40 00 01 40 40`（原来全 0），指针可用
`HKLM\...\SWOA0E01\Device Parameters\JcPointer`（DWORD，默认 1，设 0 关掉指针只留手柄）关掉做对照。

新增诊断值：`JcBadCrc`（CRC 错帧数）、`JcBadLen`（长度不符帧数）、`JcRxErr`（LSR 错误字节数）、
`JcAxisRej`（摇杆跳变被拒次数）、`JcMouseRej`（鼠标键被防抖推迟次数）、`JcPtrOn`（指针是否启用）、
`JcLastBtn`（最近一帧原始 24 bit 按键字）、`JcLastFrame`（最近一帧前 16 字节 hex）。
判读：`JcReports` 稳定增长且 `JcBadCrc/JcBadLen` 很小 → 帧干净；若 `JcBadCrc` 快速涨 → 仍是链路问题（查波特率/反相）。

### 0.3.0 上机第一批数据（2026-11-17 13:2x）

```
右手柄 ACPI\SWOA0E01: state=9 reports=640/10s frames=640 badcrc=0 badlen=0 rxerr=0 err=0 timeout=0
左手柄 ACPI\SWOA0E02: state=9 reports=640/10s frames=640 badcrc=0 badlen=0 rxerr=0 err=0 timeout=0
lastcmd=0x92 lastlen=61 lastbtn=0x008000(=bit15，未定义位，疑似固件标志，不映射到 HID 所以无副作用)
```

结论：**字节流本身是干净的**（640/10 s = 15.6 ms 一帧，帧数=报告数，无坏帧），
说明 0.2.9 的误触不是"CRC 坏帧"造成的，而是 **0.2.9 里每个字节被喂了两次（轮询直读 + 环形缓冲）**
导致帧与自己的副本交错 —— 0.3.0 的 fix #3 才是主修。后续重点是"静置还有没有误触"的主观验证。

### 0.3.1（2026-11-17 13:2x 上机，`oem32.inf`）

- 用户反馈"**光标的挪动位置跟手柄有关，手柄取下来就不会**" → 直接定位：`JcParseInputReport()` 里
  `JC_PAD Pad;` **没清零**。右手柄只写 `Axis[2]/Axis[3]`，`Axis[0]/Axis[1]` 是**上一次调用残留的栈垃圾**，
  而 `JcSubmitPointer()` 用 `Axis[0]/Axis[1]` 算 `Dx/Dy` → 右手柄那条鼠标集合被喂随机位移 → 光标自己跳；
  同理左手柄的 `Axis[2]/Axis[3]`（游戏手柄的 Rx/Ry）也是垃圾 → joy.cpl 里右摇杆会抖。
- 改成 `JC_PAD Pad = {0};`，一切正常；上机 `JcVer=301`、两手柄 state=9、badcrc/badlen 全 0。
- 教训：内核里**局部结构体必须清零**，`Pad.Buttons = 0` 只清了一个字段。

### 0.3.2（2026-11-17 13:5x 编译完成，待机器醒着时上机）

用户 0.3.1 实测："误触确实没了；joy.cpl 里左右摇杆**轻微抖动**；光标不动了；
但**放着进睡眠、唤醒后拨摇杆会锁死朝上、再朝左，过一会儿自己恢复**（像校准程序没启动）。"

1. **摇杆抖** → `jc.h` 的 `JcMapStick()` 加 `JC_STICK_DEADZONE 40`（原来是 0：12 bit 的 ±1 读数
   被放大成 ±32/32767，joy.cpl 就看得见抖）。死区外把偏移减掉再缩放，起点不跳变。
2. **睡醒锁死** → 自校准原来把**握手期接受的帧**也平均进去（那时 `State != Ready`，CRC 校验还是放宽的），
   中心可能算成 4095 之类的值 → 映射后钉死在一端；直到掉线重握手重新校准才恢复。
   现在 `JcCalFeed()`：只在 `State==Ready` 采样；单帧偏离当前均值 >400 判野值、窗口内 max-min >300
   判"手在动" → 丢弃重来；最终中心必须在 1000..3100，否则重来（最多 8 次后回落 2048）；
   校准成功 `JcCalLock=1` 后不再重算，失败则下次 attach 重试。
   新增诊断：`JcCalRej`（被拒样本数）、`JcCalLock`、`JcCentre`（高 16 位 X、低 16 位 Y 的中心值）。
3. 源码格式事故与恢复（自用工具，别再踩）：`(Get-Content x.c) -replace ... | Set-Content -NoNewline x.c`
   会把**整个文件压成一行**（数组无分隔写入）。已用 `tools/reflow-c.js`（按 token 流不变的方式补回换行）
   + `tools/rewrap-comments.js`（重排注释）+ `clang-format -style=file`（`.clang-format` 已放仓库根，
   `BreakBeforeBraces: Custom` + `AfterFunction: true`，和原风格一致）恢复，`src/` 现在只有 `jc.h`/`switchjoycon.c`，
   事故备份在 `tools/rescue/`。以后改版本号直接用 `edit` 工具，别用管道 Set-Content。

## 六、操作纪律（血泪教训）

1. **不要用** `pnputil /remove-device` + `/scan-devices` 组合，也不要 `pnputil /add-driver … /install`：会把这台机器的 PnP/服务线程卡死（SSH 只 TCP 通、banner 超时；Clash 服务也起不来）。恢复办法：关开 WiFi 或重启。
2. 换驱动版本 = **scp 文件 + 设备管理器"更新驱动程序"**（最稳）。
3. 读诊断：`HKLM\SYSTEM\CurrentControlSet\Enum\ACPI\SWOA0E01\1\Device Parameters`
   （JcState / JcReports / JcFrames / JcAckAny / JcAckAcc / JcMacSent / JcMacReply / JcLastCmd / JcLastLen / JcRxTail / JcDetect / JcLsr / JcIir / JcIerProbe / JcScratch / JcTxPackets）
   `JcState`: 0=未插 1=检测稳定 2=魔数 3=握手 4=读MAC 5=HID断 6=HID连 7=周期 8=报告模式 9=Ready
4. SSH：`ssh -i D:\paopao\ssh\woa_ed25519 woa@100.106.117.117`（Tailscale），辅助脚本 `D:\paopao\ssh\swrun.ps1 -File <ps1> -Target 100.106.117.117`。
   **机器睡着时两个地址都连不上**（Modern Standby 断 WiFi），叫醒后再试即可；远程装驱动用
   `Invoke-CimMethod -ClassName Win32_Process -MethodName Create` 起独立进程跑 pnputil，别在 SSH 会话里直接跑。
5. 编译驱动：`pwsh -File D:\paopao\switchjoycon\tools\build.ps1 -Sign`（LLVM clang-cl + WDK，内部调用
   `D:\paopao\WoA\rebuild\src\Drivers\tools\Build-Driver.ps1`，需要 `-Libs vhfkm.lib,libcntpr.lib`）。
6. 编固件：`bash D:\paopao\WoA\build\build-variants.sh vNN`（devkitPro msys2 bash，`PYTHONUTF8=1`）；
   产物 `D:\paopao\WoA\rebuild\out\bl33-swoa-vNN.bin`。改 `Dsdt.asl`/`PlatformBm.c` 时注意**不要写成 UTF-8 BOM**（iasl 会报语法错误）。
